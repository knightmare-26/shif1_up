## Commands

### Run everything (recommended for development)
```bash
npm run dev          # Starts both backend + frontend concurrently
npm run up           # Same, but supervised: health-checks both and restarts whichever stops responding
```

`scripts/health_poller.py` (stdlib only; `--check` prints status and exits, `--only backend|frontend`). It adopts servers that are already healthy, writes child output to `logs/`, and restarts whichever stops responding. A backend running against Supabase heals its own database connection (see `DatabaseGuardian` below), so the poller reports that state but doesn't restart for it; an older backend that reports `degraded` without the self-healing marker is still restarted, and `SUPABASE_ACCESS_TOKEN` (in `.env`) lets the poller restore a paused project for such a backend. A running poller also keeps a free-tier project from re-pausing, since `/health` runs `SELECT 1`.

### Backend only
```bash
python start_backend.py          # Preferred: checks deps, sets env, starts uvicorn
# or directly:
uvicorn api.main:app --reload --port 8000
```
The API is served at `http://localhost:8000`, docs at `http://localhost:8000/docs`.

### Frontend only
```bash
npm start            # React dev server on http://localhost:3000
npm run build        # Production build
```

### Tests
```bash
pytest tests/                    # All tests
pytest tests/test_api.py -v      # Single file, verbose
pytest tests/ --cov=api          # With coverage
```
Use the project venv: `venv/Scripts/python.exe -m pytest tests`. `test_api.py` covers the core read endpoints end to end (health, drivers, races, results, laps, live state, legacy standings) against data stored in the throwaway database, not mocks. `tests/conftest.py` isolates the suite from every production service before the app is imported — in-memory Redis mock, no `DATABASE_URL` (local DuckDB in a temp dir), temp `MODEL_DIR`/`CACHE_DIR`, no background model warm-up — so it never writes to the real Upstash Redis or Supabase. Keep new tests inside that isolation.

### Data ingestion
A session is stored by replacing its rows (not upserting), so a re-ingest can't leave stale rows behind. Drivers without a classified position are numbered after the classified ones (they used to share P99 and overwrite each other). **Driver names** don't come from FastF1 (it shortens some — "Kimi Antonelli" — and gives an FP1 stand-in the car owner's name): `scripts/sync_driver_names.py` sets Jolpica's name for anyone who raced (matching the standings) and OpenF1's for FP1-only stand-ins, or the three-letter code if neither knows them (`services/driver_names.py`). Ingests keep a stored name and only update the number; a new code arriving with another driver's name is looked up on OpenF1. `SimpleDuckDBService` wraps its connection in a lock (`_LockedConnection`) — it's shared by the event loop and executor threads, and overlapping use crashed the interpreter.
```bash
# Fast ingest (race results + standings, no telemetry — runs in minutes)
python ingest/simple_ingest.py --years 2024
python ingest/simple_ingest.py --years 2022 2023 2024   # also populates grid column

# Full ingest with telemetry/Parquet (takes hours, large download)
python ingest/historical_ingest.py --years 2024
python ingest/incremental_ingest.py --years 2024

# Missing FP1-FP3 only, with retries (FastF1's timing API is flaky)
python scripts/backfill_practice.py --years 2025 2026 --dry-run

# Static snapshots for FINISHED seasons (public/data); run after a season's last race
python scripts/generate_static_data.py --year 2026
```

## Architecture

Full-stack F1 analytics platform with:
- **React frontend** (`src/`) — TypeScript, TailwindCSS, React Router, Chart.js, Framer Motion
- **FastAPI backend** (`api/`) — Python, async, WebSocket support
- **DuckDB** — historical race/lap/telemetry storage (`data/f1_history.duckdb`; bundled in Docker image)
- **Supabase PostgreSQL** — users/auth table; F1 data migration approved (not yet done)
- **Upstash Redis** — live race WebSocket state + pub/sub fan-out
- **FastF1** — external F1 data source (years 2020–2024)
- **Jolpica-Ergast API** — external F1 data source for other years (ergast.com shut down 2024)

### Deployment (Render)

| Service | Type | Notes |
|---------|------|-------|
| `shif1-up-api` | Render Docker Web Service | `env: docker`; requirements at `api/requirements.txt` |
| `shif1-up-frontend` | Render Static Site | `public/_redirects` for SPA routing |

Config in `render.yaml`. Secrets (`REDIS_URL`, `DATABASE_URL`, `CORS_ORIGINS`, `SUPABASE_ACCESS_TOKEN`, `REACT_APP_API_URL`) are set in the Render dashboard — never committed. `REACT_APP_API_URL` is read at **build** time (CRA bakes it into the bundle), so changing it needs a frontend redeploy; if it's missing the site falls back to `http://localhost:8000`. Render's CI build treats lint warnings as errors, so check with `CI=true npm run build` before pushing.

**Cold starts and paused databases**: on the free plan the API host sleeps after ~15 min idle and a free Supabase project pauses after a week idle. Opening the site wakes both: the frontend pings `/health` on load, which boots the API; the API's `DatabaseGuardian` then reconnects to Supabase and, if the project is paused, restores it via the Management API (needs `SUPABASE_ACCESS_TOKEN`). A cold start of the API alone doesn't block anything: the pages render at once (Render holds their requests while the host boots), and only if it's still starting after 8s does a slim banner (`ServiceStatusBanner`) say so; a database that's merely `connecting` after boot counts as part of the cold start. Only when the **database is down** (`checks.database.state` `waking` / `unavailable` — a paused project being restored) does the frontend show the blurred full-screen wait screen (`ServiceGate`) instead of pages — steps, a timer and a "Last check" line that says exactly what the last `/health` call returned; after 2 minutes it offers *Try again* / *Open the site anyway* so it can never trap a visitor. Database-backed endpoints answer `503 database_waking` meanwhile. When the backend comes back after a request failed, the routes remount so failed loads retry.

`/health` `checks.database` reports `state`, `project_status` (what Supabase's API says: `INACTIVE`, `PAUSING`, …) and `can_restore` (whether a token is configured) — check it first when a wake-up doesn't happen: `state: unavailable` with `can_restore: false` means the server has no token, and `unavailable` with a token means Supabase reports a status the guardian can't act on (its `project_status` says which). A failing DB probe makes `/health` verify the connection immediately, so a project paused under a running API is noticed on the next page load, not at the next 60s keepalive.

### Backend service layer (`api/services/`)

| Service | Purpose |
|---|---|
| `simple_duckdb_service.py` | DuckDB historical F1 storage (drivers, races, race_results, laps, users) |
| `prediction_service.py` | LightGBM rankers (qualifying, race, sprint); walk-forward backtest; trains on the F1 database |
| `championship_service.py` | Drivers'/constructors' title outlook: exact clinch/elimination maths + Monte Carlo projection from the race ranker |
| `redis_service.py` | Real Redis client for live state and pub/sub |
| `mock_redis_service.py` | In-memory Redis mock (used when Redis is unreachable) |
| `fastf1_service.py` | FastF1 library wrapper (years 2020–2024) |
| `ergast_service.py` | Jolpica-Ergast REST API wrapper (other years) |
| `cache_service.py` | In-process cache layer for API responses |
| `db_guardian.py` | Owns the Supabase connection: connects in the background, wakes a paused project, reconnects if it drops |
| `redact.py` | `redact_url()` — keep credentials (e.g. the Upstash token) out of logs |

**Data source routing**: `api/main.py` uses `FASTF1_YEARS = [2020, 2021, 2022, 2023, 2024]` to route to FastF1 vs Jolpica-Ergast.

**Redis fallback**: On startup, tries real Redis; silently falls back to `MockRedisService` if unreachable. App runs without Redis locally.

**DuckDB fallback**: `SimpleDuckDBService` falls back to in-memory dict if DuckDB is unavailable. Seeds sample data on startup via `_load_sample_data()`.

**Postgres (Supabase)**: reads `DATABASE_URL`. When set, `DatabaseGuardian` (`services/db_guardian.py`) opens both the auth and F1-data pools — the first attempt at startup (bounded), then retrying in the background — so the API always comes up and can answer `/health` even when the project is paused. If the connection fails and `SUPABASE_ACCESS_TOKEN` is set it asks Supabase's Management API for the project state and restores it if paused, then reconnects without a restart (`SUPABASE_PROJECT_REF` is otherwise parsed from `DATABASE_URL`; `SUPABASE_API_URL` overrides the API host, for tests). While it's down, DB-backed endpoints (`/race/*`, `/predict/*` except status/circuits, `/admin/*`, `/auth/*`) answer `503 {"detail": "database_waking"}` with `Retry-After` and CORS headers. Unset `DATABASE_URL` means local DuckDB with auth disabled. `_run_query` swallows errors and returns `[]`, so don't use it to test connectivity.

### WebSocket live data flow

**Shelved (Sep 2026):** no OpenF1 subscription — it costs money the project doesn't have — so no credentials are set and the Live pages show "coming soon". Everything below is built and tested; adding the two env vars is all it would take. Admin replays of finished sessions still work.

**Source: OpenF1, relayed by the API** (`services/openf1_live.py`, `services/live_relay.py`). FastF1 only serves a session after it finishes, so live data comes from OpenF1: finished sessions are free, data *during* a session needs their paid tier (€9.90/month) — set `OPENF1_USERNAME` / `OPENF1_PASSWORD` on the API. With them, `LiveRelayManager.schedule_loop` starts a relay for every session as it begins (polls every 8s, within the paid tier's 60 requests/minute), streams it through Redis like the poller did, and runs the post-session ingest + retrain when it ends. Without them, an admin can **replay** a finished session (Data Manager → Live Timing, or `POST /admin/live/relay` with `replay_speed`): the whole session is loaded once and the board rebuilt against a moving clock — how the pipeline is tested for free. OpenF1 records are converted to the FastF1-shaped laps table `services/timing_board.py` builds the board from, adding real gaps/intervals, pit-lane status, track status from race control (green / yellow / sc / vsc / red / chequered), and "Stopped" for a car that hasn't finished a lap for 5 minutes (OpenF1 has no retirement status). The Live pages are switched on at runtime by `GET /live/status` (`useLiveTiming()` in `src/config/features.ts`): on when the live feed is connected or a relay is running, otherwise "coming soon". Local testing: never point a replay at the production Redis — the `shif1up-backend-local-redis` launch config runs the backend on the in-memory mock. The FastF1 poller below still works for local/docker use.

1. `live/poller.py` polls FastF1 for **one session per process** (`--session`, default `R`) → writes `LiveState` to Redis via `set_live_state()` + `publish_update()`. Start one poller per session you want to follow. The race id is `{year}_{gp}`; other sessions get a suffix (`2026_Belgian_Grand_Prix_FP1`) — ids are opaque to the API, Redis and WebSocket. Existing limitation: the poller calls `session.load()` and treats non-empty results as "live"; it is not a true live-timing client
2. Two state shapes, marked by `session_type`: **classified** (`R`, `S`) — FastF1 race `Position` order plus a lap counter; **timed** (`FP1-3`, `SQ`, `Q`) — ordered by best lap so far with gap to the fastest, no lap counter. Both are built from one `build_driver_rows()`, so every driver carries the same timing-board fields: `best_lap_time` + `best_lap_status` (`purple` = session fastest, else `green`), `sectors` (latest lap's S1–S3, each `purple` session best / `green` own best / `yellow` slower / `none` not set), `tyre`, `tyre_age`, `stints`, `in_pit` (dims the row), `team`, `laps_completed`; drivers with no timed lap are listed last ("No time"). Timed sessions have no classification to wait for, so they end after 5 minutes with no new lap; the end-of-session ingest sends the session
3. `api/main.py:/ws/live/{race_id}` accepts WebSocket connections, sends initial state, streams Redis pub/sub messages (one pub/sub subscription per viewer, released the moment the viewer disconnects — not at the next update); `_unwrap_live_state()` flattens Redis envelope so frontend always gets a flat `LiveState`. `POST /simulate/live/{race_id}?session=...` writes either shape for local testing (22-car field for timed sessions)
4. Frontend `LiveDataMonitor` has a Session select (Practice 1-3, Qualifying, Race; a sprint weekend — `RaceEvent.is_sprint` — is Practice 1, Sprint Qualifying, Sprint, Qualifying, Race), connects with exponential backoff, and renders `LiveTimingBoard` (a live-timing style board with **Laps / Sectors / Tyres** tabs; no *Segments* tab — those mini-sector bars need live telemetry that FastF1's lap data doesn't include). Qualifying and sprint qualifying add knockout-zone headers (Q3 = top 10, then six out in Q2, six out in Q1 on a 22-car grid; `qualifyingZone` in `utils/races.ts`) from the *current best-lap order* — exact for the final order, but mid-session eliminated drivers keep their Q1 laps. Sector/tyre data only changes when a lap completes, so the board lags the official timing screen. `LiveAnalytics` polls REST every 15s and follows the race only

### Prediction service (`api/services/prediction_service.py`)

- **Training**: starts in the background as soon as the database is ready (`_warm_prediction_models`, fired by `DatabaseGuardian`'s `on_ready` hook; local DuckDB starts it at boot), or on the first predict call, or via `POST /predict/train`. It is single-flight (`_train_lock`: the three parallel predictions on the Predictions page share one training) and the CPU-bound fit (`_fit`) runs in a worker thread on a private copy of the state that is swapped in atomically — the event loop, and so `/health`, stays responsive. Models are saved to `MODEL_DIR`, which is temporary storage on Render's free plan, so every cold start retrains (~10s locally); `/predict/status` reports `training` while it runs and the frontend shows "Models warming up" until `trained`
- **Models**: qualifying, race and sprint are each an `LGBMRanker` (lambdarank) **blended with a ridge regression** on the same inputs (`services/blend.py`, Phase 5 #34: `BlendedRanker` — score = z(ranker) + `BLEND_WEIGHT` × z(linear) within the session; the label-encoded ids are left out of the linear part). Walk-forward: qualifying 3.20 → 2.97 places off (paired t = −6.2), race 3.28 → 3.23 (t = −2.1), sprint 2.87 → 2.74, qualifying top-3 / Q3 chances better, pole slightly worse (0.0350 → 0.0355); the linear model alone did about as well as the ranker, a more regularised ranker worse (3.31) — the two make different mistakes. Weights 0.25–3 and ridge alpha 1–100 were within noise; the equal blend was set first. Grouped per race — a ranking objective, so predictions display as plain rank (#1, #2, …) with no fractional "expected position". `_fit_ranker` turns position/grid into a per-race relevance score (`field_size + 1 - value`, clipped ≥ 0; LightGBM rejects negative labels) and `_ranks_from_scores` turns scores back into ranks. Race/sprint predictions feed the qualifying *rank* in as their grid input
- **Odds** (race, sprint and qualifying; `services/finish_odds.py`, Phase 4 #33): `championship_service.with_finish_odds` plays the session out 20,000 times (Plackett-Luce) from **one strength per driver** — `beta × model score`, and in a race `− gamma × log(grid position)` with retirements drawn first (each driver's recent DNF rate shrunk halfway to 10%) — fitted by likelihood on the **top 5 finishers** of held-out races (the whole order is mostly midfield shuffling, which made one beta far too cautious at the front). Qualifying chances then go through a correction curve per market (isotonic). Six fits, picked by the situation the prediction was made in: race and sprint before their qualifying (predicted grid, `gamma` small) or after it (`grid_source` = this weekend's (sprint) qualifying: the real grid and practice), qualifying before or after practice (`practice_used`). The sprint is its own fit (a sprint model per held-out season; points = top 8; grid weight ~1.7 — sprints are processional); walk-forward on 23 sprints its chances are level with the grid-slot history (win 0.0306 vs 0.0287, podium 0.0500 vs 0.0518, points 0.0941 vs 0.0993), and Predicted vs Actual scores sprints too (`sprint_mae`, `predicted_sprint`). **A race (sprint) is re-ordered by that strength**, so its order and chances always agree (`odds_method` says what went in). Adds `expected_position` ("avg P4.8"), `win_probability`, `podium_probability` (+ `points_probability` for the race). **Why** (Phase 5): each prediction carries `factors` — every input's share of the score (LightGBM's own `pred_contrib` plus the linear terms, no SHAP library) against the session's average driver, grouped into `blend.FACTORS` (recent form, team, this circuit, practice, starting grid, reliability, driver); the odds convert them to strength units and add the grid's own term ("Predicted grid" before qualifying); an input the same for every driver (practice before any has run) goes to a hidden "Other" — the trees would otherwise credit it through interactions. The page shows the top two under each driver (▲ / ▼), all on hover. The title simulation draws its races the same way (see Championship outlook). The calibration is built in the background after training (`championship_service.warm()`); until it's ready predictions go out with `odds_available: false`. Predictions cover the drivers **entered for that weekend** (`services/entry_list.py`): the weekend's stored sessions (qualifying first, FP1 only as a last resort — rookie stand-ins), teams filled from OpenF1's entry list where FastF1 left them blank, else OpenF1's driver list for the latest started session; before a weekend starts (or while OpenF1 is locked) it falls back to the last race's line-up. Results carry `field_source`, shown on the page. A returning driver is predicted from their own history with their current team's form (`_with_teams`); a debutant gets the field's median driver inputs. Cached predictions are reused only for the same drivers in the same cars
- **Features**: rolling 5-race form, circuit history, team form (`_team_form`: worked out per race — the mean of the team's cars — over its last `TEAM_FORM_RACES` = 3 races and its past visits to the circuit; it used to be rolled over driver rows, so one teammate's row took in the other's finish from the same race. Fixing that leak left the walk-forward level — qualifying 2.976 → 2.990, race 3.223 → 3.217, sprint 2.756 → 2.841, all noise; 5 races was worse for qualifying), DNF rate, grid. **An upcoming race is predicted from the inputs its own row gets once it's run** (`_build_prediction_rows`): `_engineer` also keeps each input *after* the race (`driver_rolling_finish_after`, `driver_rolling_grid_after`, `driver_dnf_rate_after`, `constructor_rolling_finish_after`; models saved without them fall back to the old columns), the team's form is taken from the team's latest race (a driver back from a break used to get it from their own last race), its circuit average per race, and the round is the race's place on the calendar (`round_no`: `main._calendar_round` from the schedule, the title simulation's own rounds; it used to be the round the circuit usually is — 1 for a new circuit). Before, rolling form, team form and the DNF rate were one race out of date. `tests/test_upcoming_rows.py` checks the rows equal the race's engineered row (debutants aside, who get the field's median). Replaying 2025–26 the way the site predicts (40 rounds, same models): qualifying 2.770 → 2.800 places off, race from the real grid 3.405 → 3.411 — noise; the gain is that Predicted vs Actual now scores exactly what the site shows (see `RACE_FEATURES_*`, `QUALI_FEATURES`), **season-to-date form** (`services/season_form.py`, Phase 2 #31: qualifying gets the driver's average grid so far this season — last season's final average at round 1 — and the race gets driver and team points so far; an upcoming race uses the values *after* the latest race, none in a season that hasn't started, so `_build_prediction_rows` takes the race's `season`. Walk-forward: qualifying 3.80 → 3.58 rank error, paired t = −3.3, now ahead of the championship-order baseline; race 3.45 → 3.44 with slightly better win chances), plus same-weekend **practice pace** (`services/practice_features.py`, `PRACTICE_INPUTS`): best FP1–3 rank, best lap's gap to the session's fastest (%), the team's quicker car's gap, and the median gap to the teammate — each used once >50% of rows have it. Where a weekend has no practice (an upcoming race before FP1, the title simulation, a backtest weekend without practice) the inputs are the **training medians** (`_fill_practice`); filling them with 10 like the other inputs scored 4.41 quali rank error before practice — worse than a model without practice (4.18). An upcoming race uses its weekend's practice once stored (`weekend_practice`; results carry `practice_used`, shown on the page). Phase 1 (#30) walk-forward: rank only 3.89 quali / 3.49 race, all four 3.80 / 3.45 (no practice at all 4.18 / 3.57); paired per race the gap features are only t≈−1.3, but every accuracy and probability score moved the right way. **Practice (and qualifying) load themselves** during a race weekend (`services/weekend_practice.py`, run by `_data_upkeep_loop` — see Data upkeep below): every 20 min from 4 days before a race (else every 6 h) it stores each finished FP1–3 not yet stored — from OpenF1 (free for finished sessions; two small requests, far lighter than FastF1 on the 512 MB instance), 15 min after the session ends, ranked by best lap exactly like FastF1's rows (checked on 2026 Kuala Lumpur: same order and teams in all three sessions) — then retrains. It also fills in a weekend missed in the last 14 days. Anything older that's missing is filled by data upkeep; `scripts/backfill_practice.py` is for local copies
- **Accuracy**: `GET /predict/backtest` serves the cached **walk-forward** result — every race scored by a model that never saw it: earlier seasons by one model each, trained on the seasons before; the **latest season race by race**, each round by a model trained on everything up to the round before (what the live site does, since it retrains after every race). Scoring units are cached with a fingerprint of their inputs (`units`), so a rebuild refits only what changed — a new race is one refit, a corrected result refits that round onwards; bump `WALK_FORWARD_VERSION` when the method changes (a cache from an older version is rebuilt). Falls back to scoring the live model against its own training data (~3x too optimistic) only when nothing is cached. Baseline (Phase 0, #29, 7 Oct 2026, 86 races 2023–2026): 3.89 quali / 3.48 race rank error; 2026 alone 3.19 / 3.73 (3.61 / 3.64 with one model for the whole season).
  - **Chances are scored too** (`services/backtest_scores.py`, `probability_scores`): each race's pole/top-3/Q3 and win/podium/points chances by the same `FinishOdds` as the Predictions page, fitted only on earlier races (first 10 give none); a race is re-ordered by strength as on the page (the model's own order kept as `model_position`). Against *uniform* and *starting slot* (how often that grid slot won/podiumed/scored before; the race predictions know the grid): Brier, log loss, ROC-AUC, a reliability table, per-driver chances on the page. Phase 0 baseline was worse than the starting slot (win −24%, podium −30%: drivers given ~19% to win won 56%). **Phase 4 (85 races, grid known)**: win 0.0376 → 0.0259, podium 0.0886 → 0.0679, points 0.1734 → 0.1527 — now better than the starting slot (0.0312 / 0.0695 / 0.1647); pole 0.0386 → 0.0350, Q3 0.1535 → 0.1404. The order by strength: winner picked 58% → 67% (grid 58%), 3.44 → 3.27 places off (grid 3.36), podium named 62% → 67% (grid 67%). Tried and not kept: blending the chances with the slot history after the simulation (as good, but contradicts the order — keeping order cost most of the gain), separate spreads for the leaders and the rest, a per-circuit spread (no effect; so no safety-car rate either). `WALK_FORWARD_VERSION` 8
  - **Against simple guesses** (`hit_rates`): the predicted order's winner / podium / top-5 / top-10 hit rates and MAE/RMSE next to the *starting grid* (race; the race predictions know the grid) and the *championship order* going into the weekend (Grand Prix points so far, recent form breaking ties). Probability markets also carry ROC-AUC. Baseline (Phase 1 inputs, 86 races): race — model picks the winner 58% / names 62% of the podium / 3.44 places off vs the grid's 58% / 67% / 3.34, so once the grid is known the race model adds nothing over it; qualifying — model 3.77 places off vs **3.59 for the championship order**. Win/podium chances rank drivers well (AUC 0.95 / 0.93); it's their calibration that's off
  - **Sprint qualifying is scored** (`WALK_FORWARD_VERSION` 13): it's predicted by the qualifying model — a model of its own did worse with ~20 sprint weekends — so the Predictions page's Sprint Qualifying session is the qualifying prediction, and the backtest scores the same scores (`predicted_sq`, `actual_sq` ranked within the session, `sq_mae`) with the qualifying odds as they stood before the weekend (`backtest_scores.BORROWED_ODDS`: used, never fitted on; scored before qualifying so it can't see the weekend's qualifying). 23 sprint weekends: 2.99 places off vs 3.29 for the championship order, pole picked 48% vs 39%; pole chances 15% better than uniform (Brier 0.0401).
  - **A weekend under way is in it before its race**: once its sprint qualifying, sprint or qualifying is stored, `_pending_races` adds placeholder race rows (the drivers entered, no result) for weekends after the latest race, so it goes through the same feature path as every scored race; entries carry `in_progress: true` and `sessions_done`, the page labels it "(race to come)" and shows its sprint/qualifying only. Unit fingerprints hash numbers as floats, so the race arriving refits just that round. Its qualifying/sprint score is the same before and after the race lands (checked on 2026 Dutch: 1.55 / 1.09 both ways).
  - It rebuilds **by itself** in the background whenever the models have been trained on results it doesn't cover (`data_fingerprint` = race, qualifying and sprint rows + latest season, kept in the model's `_meta`; checked after every training run via `PredictionService.on_trained` and on each GET, which then answers with `updating: true` and the page re-checks every 30s). Force it with `POST /predict/backtest/refresh` (admin) or locally with `python scripts/refresh_backtest.py` (`--full` refits everything); it's stored in `prediction_cache` under `_walkforward`, which `clear_prediction_cache()` deliberately keeps. Re-run it by hand after adding practice data (doesn't change the data fingerprint, but changes the unit fingerprints)
- **Improvement plan**: issues #29–#34 (phases 0–5). Keep a change only if the walk-forward improves by more than ~0.1 rank error or the probability scores improve.
- **Preseason testing for a new era** (`services/preseason_testing.py`, Phase 3b #35): the first races of a season that starts new technical rules (`ERA_STARTS`: 2014, 2017, 2022, 2026) are predicted with the form inputs (rolling and season grid, rolling finish, circuit and team form) starting from the **testing order** — teams by their quicker car's best testing lap, then drivers — blending into the real ones over `TESTING_RACES` = 3 races (`TESTING_MODE = "rule"`; an upcoming race too, `_with_testing`). Why only era starts: in stable seasons last season's team order predicts races 1–3 far better than testing (rank correlation 0.75–0.81 vs 0.36–0.62, 2023–25), at the new rules it's the other way round (2026: testing 0.89, last season 0.68). Walk-forward on 2022 and 2026 races 1–3 (2022 testable only with 2021 added to a local copy): qualifying 2.92 → 2.53 places off (2026 2.98 → 2.26), race 4.10 → 4.05, later races within noise. Testing as model inputs was worse (the model learns from stable seasons). Not used by the title simulation (`use_testing=False`): for the season-long order last season's form did slightly better. Each season's summary (best lap per driver, compound, laps) is in `prediction_cache` (`_testing`, the year; kept by `clear_prediction_cache()`): OpenF1 from 2023, FastF1 for 2022; the upkeep loop stores the current season's from February to the first race (re-downloading only when a new testing day has finished) and any finished 2023+ season's that's missing. Qualifying positions are ranked within the session (an old row had an unclassified driver at P99 — 2026 Australia — which inflated that race's error by ~4.5 places)
- **Qualifying target**: the qualifying model learns the **qualifying result** (`QUALI_TARGET`, from stored `qualifying` sessions; the starting grid where none is stored — grid penalties, and on 2022 sprint weekends the sprint set the grid), and the backtest scores qualifying against it (`actual_quali`). Walk-forward: 0.19 places better than training on the grid (t = −2.7), even judged on the grid. Qualifying is stored for every weekend from 2022 (data upkeep fills any 2023+ gap from OpenF1; 2023's sprint qualifying is FastF1's "SS"). **Sprint qualifying comes from OpenF1** (`services/openf1_results.py`): FastF1 has no classification for it (empty positions and Q times; the ingest used to store feed order — 2024 China had Stroll on pole, not Norris), so `ingest_single_race(..., 'SQ')` takes OpenF1's `session_result`, and data upkeep re-fetches any sprint qualifying stored without times. **A race (sprint) predicted after qualifying (sprint qualifying) starts from the real order** (`_starting_order`; results carry `grid_source`), as the backtest's race model does — the weekend loader stores both from OpenF1 as they finish, and the sprint and race too (`RACES`: OpenF1's points and finishing status, the grid from the session that set it — OpenF1 has no starting grid — until the next results refresh brings FastF1's official one), so a finished session moves to Predicted vs Actual within ~15 min. Baseline after Phase 2 (86 races): qualifying 3.22 places off vs 3.48 for the championship order; race winner picked 60% vs 58% for the grid, podium 64% vs 67%
- **Tried and not kept** (walk-forward, gaps under ~0.1 rank error are noise): rolling gap to pole in qualifying (%), the team's and the teammate's (Phase 2: +0.02 / +0.12 places, worse; no gain either with the qualifying-result target — the rolling and season grid averages already carry it); predicting the gap to pole (regression) and ranking it (+0.45 places, t = +4.6; a blend +0.05); a separate sprint-qualifying model (3.36 places off sprint qualifying vs 2.81 for the qualifying model, 17 weekends — too little data; one trained on both 3.01); **treating 2026 as a new era** (Phase 3 #32, measured on the 16 races of 2026 — the only new-era season — so only big effects would show): steeper season decay (2×, 3× per year), weighting 2026 races 2–6× (race −0.03/−0.09/−0.01 for 3/4/6×: no trend, luck), race-level recency (half-life 20/40 races: worse), an era flag (worse), resetting or shrinking team form at the rule change (reset: qualifying −0.13 but from late rounds, and the race *worse* in rounds 1–5 where a reset should help most; shrink: nothing). Per-round retraining and the season-to-date inputs, which restart each season, already let the model adapt to the new cars;: teammate delta (#9); weather from Open-Meteo's archive at each circuit for the race/qualifying hours — rain, temperature, rain × a driver's past wet results — and a street-circuit flag (#10): best variant 3.88 quali / 3.45 race vs 3.94 / 3.50, with no gain on the wet races themselves, and that's with observed weather (a forecast would be worse). Training grid is already FastF1's penalty-adjusted starting grid
- **Grid data availability**: `_grid_available = grid_coverage > 0.5`; shown as status on Predictions page
- **Note**: bundled DuckDB has `grid = NULL` for existing rows — run `ingest/simple_ingest.py --years 2022 2023 2024` to populate

### Session weather and replays (`api/services/session_replay.py`)

The Race Results tab shows, under the classification, a finished session's **weather** (air/track temperature, humidity, wind speed + direction, rain — at the start, plus the ranges and whether rain fell) and a **replay**: the live timing board plus weather, played back with play/pause, speed and a scrubber (`SessionConditions.tsx`, `WeatherPanel.tsx`). Data is OpenF1's (free for finished sessions, 2023 onwards). OpenF1 keeps cancelled meetings listed (2026's April Bahrain GP, while the October round at Kuala Lumpur is also called "Bahrain Grand Prix"), so `find_session` skips cancelled meetings. **OpenF1 shuts all free access — past sessions included — while any F1 session is live** (401 "Live F1 session in progress" → `OpenF1Locked` → the endpoints answer `503 live_session_lock` and the page says it's paused). So weather is stored once fetched (`prediction_cache`, circuit_name `_weather`, kept by `clear_prediction_cache()`; `scripts/backfill_weather.py` preloads every session and waits out locks) and served from there; replays load the whole session on first play and are kept in memory only (a race's gap data is ~27k rows; 4 sessions max). `GET /api/sessions/{year}/{session}/weather?gp=` and `/replay?gp=&t=` (`gp` = the schedule's race name). The OpenF1 client bursts within the free tier's 3 requests/second and 30/minute.

### Data upkeep (`api/services/data_upkeep.py`)

**The running app keeps its own data complete and correct — a change that needs new or corrected data must add the step here (or to the weekend loop), not rely on a script run against production afterwards.** `_data_upkeep_loop` (Supabase only; `DATA_UPKEEP=0` turns it off) runs every 20 min over a race weekend and every 6 h otherwise, starting 2 min after boot:
1. the weekend's practice, sprint qualifying, qualifying, sprint and race from OpenF1 as they finish (`services/weekend_practice.py`);
2. preseason testing, February to the first race (`preseason_testing.refresh`);
3. `DataUpkeep.run`, a small batch per run (OpenF1's free tier is 30 requests/minute; FastF1 loads are heavy on the free instance): positions far past the number of drivers (an old P99 placeholder) renumbered after the classified ones; a raced round of this or last season with no results (the server slept through the 14-day results refresh) ingested from FastF1, race then sprint; for 2023 on, a raced weekend's missing practice / sprint qualifying / qualifying — and sprint qualifying stored without times — from OpenF1; preseason testing for finished seasons without it; weather for stored sessions without it; the title race's track record once a season has finished and isn't in it (`seasons_considered` records what was asked for, so it's rebuilt once a year), or when the title simulation's method changed (`TITLE_BACKTEST_VERSION`, stored as `method_version` — bump it with any change to the simulation).
Anything that changed results retrains the models, which rebuilds the walk-forward backtest. What OpenF1 doesn't have, or a FastF1 load that failed, is remembered in-process (retried after 6 h / a cold start), so a permanent gap doesn't cost requests every run. The scripts in `scripts/` are for local copies and emergencies.

### Championship outlook (`api/services/championship_service.py`)

Predictions page tab **Title Race** (`/predictions?tab=title`, `&view=constructors`; current season; the old `/dashboard?tab=title` redirects there). Two parts:
- **Exact maths**: standings from stored `race_results` (race + sprint points; countback on Grand Prix finishes only; a stale duplicate row keeps its best position). A contender is alive if scoring the max in every remaining round (25, 33 with a sprint; teams 43/58; +1 fastest lap 2019–2024) with the leader scoring nothing puts them ahead on points or countback; pure maths, so a driver who missed the latest race (injured or replaced — the data can't tell) is still alive, flagged `racing: false`, and projected to score nothing more. Clinched = no rival alive. `next_race_clinch` = the margin over P2 that clinches it at the next race
- **Projection**: 10,000 simulated seasons. Each remaining race is drawn like the Predictions page's race before qualifying (`TITLE_STRENGTH = "finish_odds"`): each driver's strength from the race ranker's score and their predicted grid (`_build_prediction_rows` per circuit, no practice), fitted on the front of held-out races (a model per season trained on earlier seasons only; the backtest leaves the tested season out — `race_pre_by_year`), with retirements; plus season-long form shocks, per driver `FORM_SHOCK_SD` = 0.75 and **per car** `TEAM_FORM_SHOCK_SD` = 0.75 (shared by both drivers — per-driver shocks cancel across a team, which left the constructors' title over-confident), chosen by the backtest's joint log score (drivers + constructors). A driver who changed teams is scored with the new team's form. Constructors sum the same simulated races. Sprint rounds for the future come from the schedule (`is_sprint`); sprint orders reuse race scores
- `GET /api/predictions/championship?year=` / `constructors-championship` (one shared computation, cached in memory per season + training run + results count). `POST /predict/championship/backtest/refresh` (admin, ~1 min) replays finished seasons round by round and caches to `prediction_cache` (`_championship`, kept by `clear_prediction_cache()`); `GET /predict/championship/backtest` serves it — the page shows it as the track record. Phases 4–5 (8 Oct 2026, 2023–2025, ~70 checkpoints; the strength, the car shock, the blended models, shocks re-tuned): drivers — champion named 74% → 77% (leader 71%), Brier 0.350 → 0.300, log −0.883 → −0.708; constructors — 76% → 81%, Brier 0.338 → 0.310, log −0.607 → −0.599; joint log −1.490 → −1.307 (before the blend the drivers were better, 0.271, and the constructors worse, 0.362). Team form without the teammate leak: joint log −1.278 — drivers champion 80%, Brier 0.303; constructors 79%, Brier 0.310 → 0.296, log −0.599 → −0.567. Remaining races from form after the latest race: joint −1.260 — drivers 77%, Brier 0.320 (worse), constructors 81%, Brier 0.276 (better). Earlier run (25 Sep 2026): 73% / 76% vs 74% / 73% for "the current leader wins". 2023–2025 only, so a rough guide

### Key API endpoints

- `GET /health` — service health: Redis + DB probes, plus `checks.database.state` (`ready` / `connecting` / `waking` / `unavailable`) when running against Supabase. Never gated; a request while the DB is down nudges the guardian to retry
- `GET /drivers`, `GET /races` — historical data (DuckDB → FastF1/Ergast fallback)
- `GET /race/{race_id}/results`, `/race/{race_id}/laps` — race detail
- `GET /live/{race_id}/state` — current live state from Redis
- `WS /ws/live/{race_id}` — WebSocket live updates
- `GET /api/drivers`, `/api/constructors`, `/api/races` — legacy endpoints (frontend uses these). Standings for years served by Jolpica (2025+) are fetched with `strict=True` and go through `_standings_or_stale`: up to 3 attempts within an 8s budget, then the last good copy, then `503 {"detail": "source_unavailable"}` — never a silent `200 []` (Jolpica rate-limits by IP and Render's free instances share one). A source that answers with no standings yet still returns `[]`. The frontend caches empty lists for ≤15s, not the full TTL
- `GET /api/driver-stats?year=` — race and sprint wins/podiums per driver, counted from the stored `race_results` (2022 onwards; the standings feed has no podiums and doesn't split sprint wins). Keyed by the three-letter `code` that `/api/drivers` rows now carry; the frontend falls back to matching by name for the committed snapshots, which lack it
- `GET /api/constructor-stats?year=` — the same per team, keyed by `constructor_id` (identical in standings and results); wins once per race, podiums per car (a one-two is two)
- `GET /live/status` — whether the Live pages are on (`live_available`: OpenF1 credentials set; `enabled`: that or a relay running) and the running relays
- `POST /admin/live/relay` `{year, gp, session, replay_speed?}`, `GET /admin/live/relays`, `DELETE /admin/live/relay/{race_id}` — start/list/stop OpenF1 relays (admin JWT or internal key); without credentials only replays
- `GET /api/sessions/{year}/{session}/weather?gp=`, `GET /api/sessions/{year}/{session}/replay?gp=&t=` — a finished session's weather and replay frames (see Session weather and replays)
- `POST /simulate/live/{race_id}` — inject mock live state for testing
- `GET /predict/status` — ML model readiness + grid data availability flag
- `GET /predict/circuits` — races still to run this season; `completed_sessions` lists a weekend's finished sprint qualifying / sprint / qualifying (checked for races within 4 days), and a weekend drops out once its race is stored
- `GET /predict/qualifying/{circuit}` — qualifying position predictions
- `GET /predict/race/{circuit}` — race finish predictions
- `POST /predict/train` — re-train models on latest DuckDB data
- `GET /api/predictions/championship?year=`, `GET /api/predictions/constructors-championship?year=` — title outlook (see Championship outlook above)
- `POST /auth/signup`, `POST /auth/login`, `GET /auth/me` — JWT auth
